# Отчет о нагрузочном тестировании и стресс-анализе T-Invest Portfolio Auditor

**Дата проведения:** 28 сентября 2026 г.  
**Инструмент:** Locust 2.46.6 (Headless)  
**Окружение:** Docker Compose (Django 5.x + PostgreSQL 16 + Redis 7 + Celery + Python 3.12)  
**Тестовый сценарий:** Мульти-эндпоинтный профиль пользователя с реальным портфелем (6 брокерских счетов, 792 позиции, расчет риск-метрик NumPy, генерация графиков Matplotlib).

---

## 1. Executive Summary (Ключевые результаты)

1. **Ускорение в 145 раз:** Внедрение архитектурного паттерна **Redis Cache-Aside** в модулях `portfolio` и `analytics` сократило медианное время отклика тяжелых аналитических эндпоинтов с **580 мс до 4 мс**, а время 95-го перцентиля (худшие 5% запросов) — с **1 100 мс до 24 мс**.
2. **Шквальный стресс-тест (500 активных сессий без пауз):** При нагрузке в **500 виртуальных инвесторов** в режиме `wait_time = constant(0)` система обработала **5 172 запроса за 30 секунд** с нулевым уровнем ошибок (**0.00% fails**) и стабильным показателем **173 RPS**.
3. **Определение точки отказа (Breaking Point):** При шквальной нагрузке в **1 000 параллельных клиентов без пауз** достигнут физический предел очереди сокетов бэкенда (`Broken pipe`, 41% таймаутов). Выявлена необходимость внедрения Nginx reverse-proxy с пулом соединений и продакшн WSGI/ASGI сервера с асинхронными воркерами.

## 4. Что именно было изменено в кодовой базе (Архитектурный разбор)

### В чем заключалась проблема «ДО»?
При открытии приложения пользователем происходили следующие вычисления:
1. Запрос в PostgreSQL за снимками по всем 6 счетам инвестора.
2. Подтягивание 792 записей позиций (акции, облигации, фонды) и склейка их по `figi` / `ticker` через циклы Python.
3. Расчет доходности по формулам сложных процентов.
4. Построение матриц доходности и математический анализ на NumPy (ковариация, годовая волатильность, коэффициент Шарпа, максимальная просадка).

**Итог:** На каждый HTTP-запрос процессор сервера тратил от 340 до 1 100 миллисекунд. При 100 одновременных клиентах запросы выстраивались в огромную очередь.

### Что было внедрено: паттерн Cache-Aside (Lazy Caching)
В сервисный слой были добавлены ключи кэширования с временем жизни (TTL) 300 секунд (5 минут):

```python
# Паттерн Cache-Aside в Django + Redis
def get_consolidated_analytics(user, days: int = 90, risk_free_rate: float = 0.18):
    cache_key = f"analytics:consolidated:{user.id}:{token_id}:{days}"
    
    # Шаг 1: Проверяем наличие готового результата в RAM Redis
    cached_res = cache.get(cache_key)
    if cached_res:
        return cached_res  # Возврат за 2-4 миллисекунды без касания Postgres и NumPy!

    # Шаг 2: Если в кэше пусто (Cache Miss), выполняем тяжелый расчет один раз
    result = _calculate_numpy_risk_metrics(...)

    # Шаг 3: Сохраняем результат в Redis на 5 минут
    cache.set(cache_key, result, timeout=300)
    return result
```

**Результат:** Все последующие запросы от клиента или дашборда читаются напрямую из оперативной памяти Redis. Нагрузка на базу данных PostgreSQL и процессор упала практически до нуля.

## 5. Анализ точки отказа (Root Cause Analysis: 1 000 клиентов)

При прогоне на 1 000 клиентов без пауз Locust зафиксировал ошибки `Broken pipe` и HTTP 500.

### Причина сбоя:
1. **Предел очереди сокетов (Backlog saturation):** Когда 1 000 параллельных процессов обращаются к одному TCP-порту без задержки, очередь входящих соединений ядра ОС (`SOMAXCONN` / `tcp_max_syn_backlog`) переполняется.
2. **Таймаут клиента и сброс соединения:** Клиенты закрывают соединение по внутреннему таймауту, в то время как сервер всё ещё пытается записать HTTP-ответ в закрытый сокет (классический `Broken pipe from 172.19.0.1`).
3. **Dev-сервер вместо Production WSGI:** Сервер внутри контейнера запущен в режиме разработки без буферизации Nginx.

### Архитектурные рекомендации для Production:
1. **Nginx Reverse Proxy:** Включение буферизации запросов, пула `keepalive`-соединений и директив `limit_req` для сглаживания всплесков.
2. **Gunicorn с асинхронными воркерами:** Использование `gunicorn -k uvicorn.workers.UvicornWorker` или `gevent` с параметром `--backlog 2048` и `--workers 4`.
3. **PgBouncer:** Пул соединений для PostgreSQL для предотвращения исчерпания `max_connections`.

## 6. Как правильно тестировать LLM (Gemini Pro) под нагрузкой?

### Почему нельзя пускать шквальный стресс-тест напрямую в API Google Gemini?
1. **Строгие квоты (Rate Limits):** Даже на платной подписке (Tier 1/2) действуют жесткие ограничения:
   - Лимит запросов в минуту (RPM): 360–1 000 RPM.
   - Лимит токенов в минуту (TPM): от 1 000 000 до 4 000 000 TPM.
   При шквале в 100 RPS квота исчерпается за 3–4 секунды, после чего API начнет возвращать ошибку `429 Too Many Requests (Resource Exhausted)`.
2. **Финансовые затраты:** 100 000 прямых запросов со сложным контекстом портфеля (prompt ~2 000 токенов) сожгут сотни долларов на токены за несколько минут.

### Промышленный стандарт тестирования AI-систем:
1. **Асинхронная очередь задач (Celery + Redis):**
   Пользовательский HTTP-запрос `/api/v1/ai/audit/` не ждет генерации ответа LLM 5–10 секунд. Он моментально (за 5 мс) возвращает `task_id` и статус `PENDING`.
2. **Rate Limiter на воркере:**
   Celery Worker забирает задачи из очереди со строго контролируемой частотой (например, `rate_limit='5/s'`), гарантируя соблюдение квот Gemini API без ошибок 429.
3. **Mock LLM Provider для нагрузочных тестов бэкенда:**
   Чтобы протестировать способность архитектуры принять 100 000 обращений к AI:
   - Включается тестовый мок (`MOCK_LLM=True`), имитирующий сетевую задержку модели в 1.5–2 секунды без отправки реального трафика в Google.
   - Это позволяет проверить надежность очередей Redis, устойчивость воркеров Celery и целостность транзакций базы данных без сжигания денег.

## 7. Формулировка для резюме и портфолио (Backend / Highload)

> **Оптимизация производительности и стресс-тестирование (T-Invest Portfolio Auditor):**
> * Спроектировал и провел сценарии нагрузочного тестирования распределенной системы на базе **Locust** (до 1 000 параллельных сессий, шквальный трафик без задержек).
> * Выявил узкие места в ресурсоемких математических расчетах (NumPy, агрегация сотен позиций с 6 брокерских счетов) и внедрил паттерн **Redis Cache-Aside**, добившись **ускорения медианного времени отклика в 145 раз (с 580 мс до 4 мс)** и p95 в 45 раз.
> * Провел стресс-тест на определение точки отказа (Breaking Point): система подтвердила устойчивость при **173 RPS (500 одновременных пользователей без пауз с 0% ошибок)**. Диагностировал причины деградации сокетов (`Broken pipe`) на 1 000 одновременных соединениях и разработал архитектурный план масштабирования через Nginx, Gunicorn и PgBouncer.
