## 🧭 Общая концепция и архитектура системы

Цель проекта — создать надежный многопользовательский сервис, который по расписанию собирает данные из API Т-Банка, консистентно сохраняет историю портфелей в базу данных и предоставляет доступ к аналитике через REST API и Telegram-бота.

### Архитектурная схема (Микросервисное разделение):
```text
[ T-Bank gRPC API ]
       ▲
       │ gRPC (t-tech-investments)
       ▼
[ Celery Workers ] ◄── Очередь задач ── [ Redis (Docker) ] ◄── Будильник ── [ Celery Beat ]
       │
       ▼ Запись в транзакции (bulk_create)
[ PostgreSQL / SQLite ]
       ▲
       │ Чтение через ORM
[ Django REST API (DRF) ]
       ▲
       │ HTTP / JSON (aiohttp)
[ Telegram Bot (Aiogram 3.x) ]
```

## 🛠 Хронология этапов: Что, Зачем и Почему

---

### Этап 1. Модели данных и стратегия хранения (Схема БД)

#### Что сделали:
Описали 4 ключевые сущности в Django ORM:
1. `InvestorUser` (`telegram_id`, `encrypted_token`, методы шифрования Fernet).
2. `Account` (брокерский счет в Т-Банке, `account_id`, тип, статус).
3. `PortfolioSnapshot` (снимок портфеля на конкретный момент времени: общая сумма, акции, облигации, фонды, кэш, доходность).
4. `Position` (конкретная бумага: `figi`, количество, цена, средняя цена, доходность).

#### Зачем:
Заложить фундамент для сбора истории и будущей аналитики.

#### Почему именно так (Архитектурный выбор):
* **Паттерн Append-only Snapshots (таймсерии) вместо перезаписи одной строки:**  
  Если бы мы хранили только «текущий баланс», перезаписывая одну запись, мы бы никогда не смогли построить график доходности за месяц, рассчитать максимальную просадку (Drawdown) или сравнить структуру активов во времени. Снимки позволяют видеть историю портфеля в динамике.

### Этап 2. Транзакции и пакетная оптимизация (Сервисный слой)

#### Что сделали:
Создали сервисный слой `backend/apps/portfolio/services.py` с функцией `save_portfolio_snapshot`:
* Обернули сохранение снимка и позиций в `with transaction.atomic():`.
* Заменили поштучное создание записей в цикле на пакетную вставку `Position.objects.bulk_create(...)`.
* Подключили штатные утилиты SDK `money_to_decimal` и `quotation_to_decimal`.

#### Зачем:
Обеспечить абсолютную целостность данных (ACID) и высокую скорость записи.

#### Почему именно так:
* **Зачем транзакция (`transaction.atomic`):**  
  Если у пользователя 50 акций, и на 20-й акции моргнет сеть или упадет база, без транзакции в базе останется снимок-«калека» (баланс 500 000 ₽, а акций сохранено всего на 10 000 ₽). Это сломает все графики. Транзакция гарантирует: либо сохраняется всё, либо при ошибке происходит автоматический `ROLLBACK`.
* **Зачем `bulk_create`:**  
  Обычный цикл `.create()` выполняет 50 отдельных сетевых SQL-запросов `INSERT`. Метод `bulk_create` собирает объекты в оперативной памяти Python и отправляет в базу **ровно один** SQL-запрос `INSERT INTO ... VALUES (...), (...)`. Это ускоряет запись в десятки раз.
* **Золотое правило сети и БД:**  
  Сетевой запрос в Т-Банк делается **до** транзакции, чтобы не держать открытую транзакцию и локи в базе во время сетевых лагов.

### Этап 3. Безопасная синхронизация счетов (`update_or_create`)

#### Что сделали:
Применили метод `Account.objects.update_or_create(account_id=acc.id, defaults={...})`.

#### Зачем:
Связать внешние счета из банка с нашими моделями без дублей и сбоев.

#### Почему именно так:
* Если делать обычный `create()`, то при втором запуске скрипт упадет с ошибкой `UNIQUE constraint failed: account_id`.
* Метод `update_or_create` атомарно ищет запись по уникальному `account_id`: если счет уже есть — обновляет его свойства (например, пользователь переименовал счет в приложении банка); если счета нет — создает новую запись.

### Этап 4. Фоновые задачи и очереди (Celery + Celery Beat + Redis)

#### Что сделали:
1. Развернули Redis в Docker через `docker-compose.yml`.
2. Настроили точку входа Celery в `backend/config/celery.py`.
3. Обернули синхронизацию в фоновую задачу `@shared_task`.
4. Настроили планировщик `Celery Beat` на периодический запуск.

#### Зачем:
Снять нагрузку с основного приложения и сделать синхронизацию автономной.

#### Почему именно так:
* Сетевые запросы в сторонний банк — долгие и непредсказуемые (2–5 секунд). Если выполнять их в веб-запросе или в телеграм-боте, сервер зависнет.
* Celery делегирует задачу фоновому воркеру, моментально освобождая интерфейс.
* Celery Beat выполняет роль автономного будильника: данные обновляются каждый час даже ночью, когда ботом никто не пользуется.
* Внутри воркеров Celery код выполняется синхронно, что позволило использовать удобный синхронный `Client` из SDK Т-Банка без танцев с `sync_to_async`.

### Этап 5. Отказоустойчивость: Rate Limits и Exponential Backoff

#### Что сделали:
Настроили параметры задачи Celery:
```python
@shared_task(
    bind=True,
    autoretry_for=(RequestError, ConnectionError),
    retry_backoff=True,
    retry_backoff_max=300,
    retry_jitter=True,
    max_retries=5,
)
```
И добавили отсечение невалидных токенов (проверка на `UNAUTHENTICATED` / `401`).

#### Зачем:
Защитить систему от блокировок банка (Rate Limits) и кратковременных обрывов интернета.

#### Почему именно так:
* **Rate Limits (Лимиты Т-Банка):** При превышении RPS банк возвращает `RESOURCE_EXHAUSTED`. Если пытаться долбить банк снова мгновенно (в ту же секунду) — токен заблокируют за DDoS/спам.
* **Экспоненциальный откат (Exponential Backoff):** Пауза перед повтором растет по формуле $2^{\text{попытка}}$ (2с $\to$ 4с $\to$ 8с $\to$ 16с). Мы даем удаленному серверу банка восстановиться.
* **Не спать в воркере:** Celery не вызывает `time.sleep()`, а возвращает задачу в Redis с меткой времени (ETA). Воркер свободен для других задач.
* **Отсечение мертвых токенов:** Если пользователь отозвал токен (401), нет смысла повторять попытку 5 раз — таска сразу логирует ошибку и останавливается.

### Этап 6. Мультитенантность и безопасность (Паттерн Fan-out)

#### Что сделали:
1. Разделили синхронизацию на две задачи:
   * **`sync_user_portfolio(user_id)`** — воркер одного инвестора.
   * **`sync_portfolios()`** — легкий диспетчер для Celery Beat.
2. Подключили шифрование токенов по стандарту Fernet (`user.set_token` и свойство `user.decrypted_token`).

#### Зачем:
Поддержка неограниченного числа пользователей и безопасность персональных данных.

#### Почему именно так:
* **Изоляция сбоев:** Если у одного пользователя упадет сеть или окажется невалидный токен, его персональная задача упадет в изолированном воркере, а все остальные пользователи успешно обновятся.
* **Параллелизм:** Несколько воркеров могут обрабатывать разных инвесторов одновременно.
* **Zero-Knowledge хранение:** Токены лежат в БД в зашифрованном виде (Fernet) и расшифровываются в памяти только на доли секунды во время обращения к API.

### Этап 7. Витрина данных: REST API (Django REST Framework)

#### Что сделали:
1. Описали сериализаторы: `AccountSerializer`, `PositionSerializer` и вложенный `PortfolioSnapshotSerializer`.
2. Реализовали контроллер `AccountViewSet(viewsets.ReadOnlyModelViewSet)`.
3. Добавили кастомное действие `@action(detail=True)` ➔ `/api/v1/accounts/{id}/latest_snapshot/`.
4. Подключили автоматический роутер `DefaultRouter`.
5. Добавили оптимизацию `prefetch_related("positions")`.

#### Зачем:
Предоставить чистый, стандартный JSON-интерфейс для Telegram-бота, WebApp и сторонних клиентов.

#### Почему именно так:
* **Zero-Trust и слабая связанность:** Telegram-бот не лезет в базу данных напрямую. Он общается с бэкендом как внешний клиент по протоколу HTTP (GET-запросы).
* **Поддержка WebApp/Mini Apps:** Telegram Mini Apps строятся на JavaScript/React — они в принципе не могут работать с Django ORM, им необходим чистый REST API.
* **Защита от N+1:** Благодаря `prefetch_related("positions")` выборка снимка и всех его акций делается за 2 оптимизированных SQL-запроса, а не за 50+.
